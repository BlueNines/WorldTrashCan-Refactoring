# WorldListTrashCan 新架构方案

## 核心方向

重构不是把旧代码拆成更多类，而是把“业务规则”和“服务端版本差异”分开。

用户明确要求：不同版本必须有明确的不同实现，不能继续把版本兼容散落在业务代码里，否则项目会再次变得臃肿。

## 总体架构 v2

上一版方案只说了 `platform/` 分包，但这还不够。真正要避免臃肿，必须在构建产物层面也分开版本实现。

正式目标改为：

```text
共同核心 + 多版本插件产物
```

也就是说，业务规则尽量复用，但不同服务端版本有不同 jar，不把 1.12、现代 Paper、Folia 的 API 强行塞进同一个运行产物里。

## 多模块结构

```text
bl-world-trashcan-parent/
  bl-world-trashcan-core/
  bl-world-trashcan-config/
  bl-world-trashcan-storage/
  bl-world-trashcan-shared-bukkit/
  bl-world-trashcan-platform-legacy-1_12/
  bl-world-trashcan-platform-bukkit-1_13_1_15/
  bl-world-trashcan-platform-paper-1_16_1_20/
  bl-world-trashcan-platform-folia-1_20/
  bl-world-trashcan-plugin-legacy-1_12/
  bl-world-trashcan-plugin-bukkit-1_13_1_15/
  bl-world-trashcan-plugin-paper-1_16_1_20/
  bl-world-trashcan-plugin-folia-1_20/
```

### core

`core` 只能放纯业务规则，尽量不直接 import Bukkit API。

可以放：

- 清理决策。
- 垃圾桶路由。
- 实体/物品策略。
- 配置对象。
- 结果统计。
- 迁移规则。

不能放：

- `Bukkit`。
- `Player`。
- `World`。
- `ItemStack`。
- `Entity`。
- Folia Scheduler。
- Paper 专属事件。

### shared-bukkit

`shared-bukkit` 只放所有版本都稳定存在的 Bukkit 适配代码。

这里也要克制，能不放就不放。只要某个 API 在 1.12、1.13、1.16、Folia 之间存在语义差异，就不能塞到 shared-bukkit。

### platform-*

每个 `platform-*` 编译时绑定自己的服务端 API。

示例：

```text
platform-legacy-1_12
  编译依赖 Paper/Spigot 1.12.2
  Java 8
  不使用 api-version
  不引用 PersistentDataContainer
  不引用现代 Adventure / RGB API

platform-bukkit-1_13_1_15
  编译依赖 Bukkit/Paper 1.13-1.15 API
  Java 8
  处理扁平化 Material 后的差异

platform-paper-1_16_1_20
  编译依赖 Paper 1.20.4 API
  Java 17 或按目标服确认
  使用 PDC、现代消息能力、Paper 能力探测

platform-folia-1_20
  编译依赖 Folia API
  Java 17
  第一阶段接入 Global Scheduler，后续实服验证后再把清理扫描升级为 Region / Entity Scheduler
  完整 Folia region-safe 必须通过实服验证，不能只靠普通 Paper 编译通过
```

### plugin-*

每个 `plugin-*` 是最终产物模块，包含自己的 `plugin.yml`。

输出示例：

```text
BlWorldTrashCan-legacy-1.12.jar
BlWorldTrashCan-bukkit-1.13-1.15.jar
BlWorldTrashCan-paper-1.16-1.20.jar
BlWorldTrashCan-folia-1.20.jar
```

这些 jar 可以保持同一插件名、同一主命令和同一数据目录，也可以按后续需求拆分。优先保持做服技术的使用习惯一致。

主类只负责：

1. 创建上下文。
2. 加载配置。
3. 创建当前产物绑定的平台实现。
4. 注册功能模块。
5. reload / disable 时按顺序释放资源。

主类禁止直接写具体业务逻辑。

## 平台选择原则

正式版本不依赖一个巨大的运行时 `PlatformFactory` 跨版本选择实现。

每个 jar 在编译期已经确定平台族：

```text
legacy jar -> LegacyPlatform
bukkit jar -> BukkitPlatform
paper jar -> PaperPlatform
folia jar -> FoliaPlatform
```

运行时只允许做同一平台族内部的能力探测，例如：

- Paper 1.18 是否存在某个可选事件。
- 1.16 是否支持 RGB。
- Vault / PlaceholderAPI 是否安装。

禁止在同一个产物里同时装入 1.12、1.20 和 Folia 的大块实现。

## API 防火墙

必须有明确的导入边界：

```text
core
  禁止 import org.bukkit.*
  禁止 import io.papermc.*
  禁止 import net.md_5.*

config / storage
  禁止 import 具体版本 API
  可以使用 Bukkit-independent 的文件和 YAML 工具

shared-bukkit
  可以 import 最低共同 Bukkit API
  禁止 import Folia
  禁止 import 只在现代版本存在的类

platform-legacy-1_12
  只能 import 1.12.2 可用 API

platform-folia-1_20
  可以 import Folia API
  但不能被其他平台模块依赖
```

后续可以用简单脚本或 ArchUnit 测试做导入扫描，只要 shared/core 误 import 高版本 API，就直接构建失败。

## 平台端口

平台端口只保留真实差异，不做空泛接口：

```text
ServerPlatform
  scheduler()
  messageSender()
  itemTagService()
  entityAccess()
  signAccess()
  inventoryAccess()
  capabilityReport()
```

业务层不出现下面这种代码：

```java
if (isFolia) {
    ...
} else if (isPaper) {
    ...
} else if (isLegacy) {
    ...
}
```

这种判断只能出现在 `PlatformFactory` 或具体平台实现内部。

在 v2 方案中，跨平台大选择由不同 jar 解决；`PlatformFactory` 如果存在，只能做同产物内部的小能力选择。

## 平台实现边界

平台实现不只是“工具类不同”，而是每条版本线有自己完整、明确的实现。

### 调度

```text
SchedulerAdapter
  LegacyBukkitSchedulerAdapter
  ModernBukkitSchedulerAdapter
  PaperSchedulerAdapter
  FoliaSchedulerAdapter
```

清理任务只写一份业务逻辑，调度器决定怎么执行：

- Bukkit/Paper：主线程 `runTaskTimer`。
- Folia：Global / Region / Entity Scheduler 按安全边界调度。

禁止继续维护 `ClearItemsTask` 和 `FoliaClearItemsTask` 两个大而重复的类。

### 消息发送

```text
MessageSender
  LegacyBungeeMessageSender
  BukkitMessageSender
  ModernAdventureMessageSender
  FoliaSafeMessageSender
```

差异点：

- ActionBar。
- Title。
- RGB 颜色。
- 点击聊天组件。
- BossBar。

业务层只调用 `messageSender.sendActionBar(...)`、`sendTitle(...)`、`sendClickableMessage(...)`。

### 物品标记

```text
ItemTagService
  UnsupportedItemTagService
  LegacyLoreItemTagService
  PersistentDataItemTagService
```

差异点：

- 新版本可用 `PersistentDataContainer` 标记玩家 UUID。
- 旧版本不能直接依赖 PDC，需要用 lore、NBT 兼容库或直接关闭该能力。

这里要明确版本能力，而不是在掉落监听里到处判断 `VersionFlag`。如果旧版本的物品标记不够安全，就宁可在 legacy 产物中禁用“玩家主动丢弃物品长期追踪”，也不要用脆弱实现伪装成完整支持。

### 告示牌与方块

```text
SignAccess
  LegacySignAccess
  ModernSignAccess
```

差异点：

- 旧版本告示牌 Material 和文本 API。
- 新版本悬挂牌、告示牌正反面等 API。

世界垃圾桶创建和识别只走 `SignAccess`。

### 实体访问

```text
EntityAccess
  BukkitEntityAccess
  PaperEntityAccess
```

差异点：

- Paper EntityMoveEvent 是否存在。
- Folia 下跨区域实体访问限制。
- 旧版本 `Enemy` 接口、实体类型名字差异。

实体清理规则不直接判断服务端版本，只接收统一的实体描述。

### 背包与 GUI

```text
InventoryAccess
  LegacyInventoryAccess
  BukkitInventoryAccess
  ModernInventoryAccess
```

差异点：

- 旧版本物品材质名。
- GUI 标题和 `InventoryView` 行为差异。
- 点击事件中的 slot 语义。
- 现代版本自定义模型数据。

GUI 业务只描述页码、按钮、权限和物品语义，具体物品构造交给平台实现。

## 能力矩阵

每个产物必须生成一份能力矩阵，写进 README 和启动日志。

```text
能力                         legacy-1.12  bukkit-1.13-1.15  paper-1.16-1.20  folia-1.20
定时清理掉落物               支持          支持               支持              支持
世界垃圾桶                   支持          支持               支持              限制支持
公共垃圾桶 GUI               支持          支持               支持              支持
个人垃圾桶                   支持          支持               支持              支持
玩家丢弃物 PDC 追踪          不支持        视 API             支持              支持
RGB 消息                     不支持        不支持             支持              支持
现代告示牌双面 API           不支持        不支持             支持              支持
Paper EntityMoveEvent        不支持        视服务端           支持              不依赖
Folia 区域安全调度           不支持        不支持             不支持            支持
```

启动时输出示例：

```text
[BlWorldTrashCan] Platform: legacy-1.12
[BlWorldTrashCan] Capability item-pdc-tag: disabled
[BlWorldTrashCan] Capability rgb-message: disabled
[BlWorldTrashCan] Capability world-trash: enabled
```

这样做服技术和测试日志都能一眼看出当前 jar 到底支持什么。

## 功能模块

每个功能模块实现一个很薄的生命周期：

```text
Feature
  enable()
  reload()
  disable()
```

推荐模块：

```text
WorldTrashFeature
GlobalTrashFeature
PersonalTrashFeature
CleanupFeature
EntityLimitFeature
ChatLimitFeature
DropProtectionFeature
SimpleOptimizeFeature
PlaceholderFeature
VaultFeature
```

模块可以依赖平台能力，但不能自己检测版本。

每个模块还要声明能力需求：

```text
FeatureDescriptor
  id
  enabledByConfig
  requiredCapabilities
  optionalCapabilities
```

例子：

```text
PersonalTrashFeature
  requiredCapabilities:
    - inventory-basic
  optionalCapabilities:
    - item-pdc-tag

FoliaWorldTrashFeature
  requiredCapabilities:
    - region-scheduler
    - block-region-access
```

如果能力不足，模块必须明确降级或拒绝启用，并在日志中输出原因。不能悄悄注册半个功能。

## 分版本功能实现

功能模块可以有分版本实现，不强求一个 Feature 跨所有版本。

```text
feature/worldtrash/
  WorldTrashFeature.java
  legacy/LegacyWorldTrashFeature.java
  modern/ModernWorldTrashFeature.java
  folia/FoliaWorldTrashFeature.java
```

选择规则：

- 如果只是调度方式不同，优先复用同一个业务 Feature，差异放到 `SchedulerAdapter`。
- 如果行为边界真的不同，例如 Folia 世界垃圾桶需要区域安全扫描，则允许单独 `FoliaWorldTrashFeature`。
- 如果旧版本缺关键能力，例如 PDC 物品追踪，则 legacy 产物可以提供能力删减版 Feature，不能把现代逻辑塞进去再到处判空。

## 清理核心

清理逻辑只保留一份：

```text
CleanupService
  scanWorld()
  handleItem()
  handleEntity()
  buildResult()
```

物品结果：

```text
SKIP
MOVE_TO_WORLD_TRASH
MOVE_TO_PERSONAL_TRASH
MOVE_TO_GLOBAL_TRASH
REMOVE
```

实体结果：

```text
SKIP
REMOVE
KILL_WITH_DROPS
```

Folia 和 Bukkit 的差异不允许复制清理规则，只能体现在 `SchedulerAdapter` 和 `EntityAccess`。

更精确地说，清理核心拆成三层：

```text
CleanupPlanBuilder
  读取配置对象，决定这轮要扫描什么。

CleanupExecutor
  通过平台访问世界、实体、方块和背包。

CleanupPolicy
  纯决策：这个物品/实体应该跳过、移动还是删除。
```

其中 `CleanupPolicy` 必须尽量纯 Java，可单元测试；`CleanupExecutor` 才允许接触 Bukkit/Folia 对象。

## 领域对象

为了避免 core 直接依赖 Bukkit，同时又不搞过度抽象，只定义少量领域快照：

```text
ItemSnapshot
  materialKey
  amount
  displayName
  lore
  ownerUuid

EntitySnapshot
  typeKey
  name
  customName
  living
  monsterLike
  projectile
  insideBoat

WorldSnapshot
  name

TrashRoute
  WORLD_TRASH
  PERSONAL_TRASH
  GLOBAL_TRASH
  REMOVE
  SKIP
```

平台层负责把 Bukkit `ItemStack` / `Entity` 转成快照。core 只看快照做决策。

这个抽象是必要的，因为它防止高版本 API 污染 core；不允许继续扩展成复杂实体模型。

## 配置拆分

新配置直接按业务拆分：

```text
config.yml
cleanup.yml
trash.yml
entity-limits.yml
protections.yml
messages/message_zh.yml
data/worlds.yml
```

运行期代码只读新配置对象。

旧配置由迁移器读取：

```text
LegacyConfigMigrator
  readOldConfig()
  readOldData()
  writeNewFiles()
```

迁移完成后，业务代码不再访问旧路径。

## 配置版本策略

配置也要区分“通用配置”和“平台差异配置”。

```text
config.yml
  language
  debug
  storage
  migration

platform.yml
  target: auto
  disabled-capabilities: []
  strict-capability-check: true

cleanup.yml
trash.yml
entity-limits.yml
protections.yml
```

`platform.yml` 不允许写大量业务项，只用于声明平台能力和降级策略。

如果某个配置项只在某个版本支持，必须在注释里写清楚：

```yaml
# 是否记录玩家主动丢弃物品的所属玩家。
# 仅 modern-paper-1.16-1.20 与 folia-1.20 完整支持。
# legacy-1.12 产物会忽略该项并在启动日志中提示能力不可用。
track-player-dropped-items: true
```

禁止让同一个字段在不同版本中表现完全不同却不写明。

## 推荐版本线与产物

为了避免一个 jar 里塞过多兼容逻辑，按以下版本能力分线：

```text
legacy-1.12
  只保留可稳定支持的旧版本能力。
  不强行支持 PDC、现代 RGB、现代告示牌 API。

bukkit-1.13-1.15
  使用 Bukkit 主线程模型。
  处理 Material 名称和聊天能力差异。

modern-paper-1.16-1.20
  使用 PDC、现代 RGB、Paper 能力探测。

folia-1.20+
  使用 Folia 调度实现。
  严格避免跨区域直接访问。
```

正式方案使用不同构建产物，不再把“同 jar + 大平台工厂”作为目标架构。

过渡阶段允许先做一个现代 Paper 产物验证业务模型，但一旦开始兼容 legacy 或 Folia，就必须拆产物。

## 构建与发布策略

每条版本线独立构建：

```text
mvn -pl bl-world-trashcan-plugin-legacy-1_12 package
mvn -pl bl-world-trashcan-plugin-bukkit-1_13_1_15 package
mvn -pl bl-world-trashcan-plugin-paper-1_16_1_20 package
mvn -pl bl-world-trashcan-plugin-folia-1_20 package
```

发布目录：

```text
dist/
  legacy-1.12/
    BlWorldTrashCan-legacy-1.12.jar
    README.md
    capability-matrix.md
  bukkit-1.13-1.15/
  paper-1.16-1.20/
  folia-1.20/
```

每个产物目录必须包含：

- jar。
- 对应版本 README。
- 能力矩阵。
- 默认配置。
- 迁移说明。
- 测试日志摘要。

## 测试矩阵

每条版本线必须有独立测试，而不是用一个版本测试结果替代全部版本。

```text
legacy-1.12
  Paper 1.12.2 测试服
  不验证 PDC
  验证旧消息、旧材质、旧告示牌、基础清理、GUI

bukkit-1.13-1.15
  至少一个 1.13/1.15 服务端
  验证扁平化材质、基础清理、GUI

paper-1.16-1.20
  Paper 1.20.4 或目标版本
  验证 PDC、RGB、现代消息、公共垃圾桶、个人垃圾桶

folia-1.20
  Folia 测试服
  验证调度安全、区域访问安全、清理不会跨区域异常
```

共同测试用例要放在 `test-specs/`：

```text
test-specs/
  cleanup-basic.yml
  world-trash-basic.yml
  global-trash-gui.yml
  personal-trash.yml
  entity-clean-policy.yml
```

每个产物跑同一批能跑的规格；因能力缺失跳过的项目必须写入报告，不能算作通过。

## 迁移策略

旧项目迁移不能靠“代码里兼容所有旧字段”。

正确方式：

```text
LegacyConfigMigrator
  输入旧 config.yml + data/data.yml
  输出新多文件配置 + data/worlds.yml
  生成 migration-report.md
```

迁移器允许读取旧路径，正式业务代码不允许读取旧路径。

迁移报告至少包含：

- 读取到的旧版本字段。
- 成功迁移的字段。
- 被废弃的字段。
- 因目标版本能力不足而无法迁移的字段。
- 需要人工确认的字段。

## 兼容策略

插件名、命令、权限和数据目录建议默认兼容：

```text
name: BlWorldTrashCan 或保留 WorldListTrashCan 待确认
commands:
  WorldListTrashCan
  WTC
  wtc
permissions:
  保留旧权限作为 alias 或继续生效
data-folder:
  需要单独确认是否沿用 WorldListTrashCan
```

如果为了品牌或新架构改名，必须提供旧命令别名和迁移说明。

## 禁止事项

- 禁止业务类直接调用 `Bukkit.getServer().getVersion()` 判断版本。
- 禁止业务类直接读取 `main.getConfig()`。
- 禁止重复维护 Bukkit 和 Folia 两套清理业务。
- 禁止在一个方法里同时处理配置解析、版本判断、业务决策和消息发送。
- 禁止新增无意义的接口、工厂套工厂；只有真实版本差异、真实外部依赖差异才允许抽象。
- 禁止普通轻量产物同时直接依赖 legacy、modern Paper 和 Folia API。
- 禁止 core/shared 模块 import 具体高版本 API。
- 禁止用反射绕过清晰的平台边界，除非是极小的能力探测，或是专门的 universal bootstrap 为了延迟加载平台模块；这两种情况都必须写测试。
- 禁止把“此版本不支持”的功能伪装成已支持；必须在能力矩阵、启动日志和 README 里明说。

## 通用总包补充方案

保留轻量分版本 jar 是基础架构，不改变。为了兼容服主习惯，可以额外交付一个 `universal` 总包，但它必须遵守以下边界：

- universal 只是启动壳和命令适配层，不复制四份业务规则。
- universal 主类按 Java 8 编译，不能直接 import Paper 1.16+、Folia 或其它高版本运行时 API。
- 高版本 platform/plugin 类只能通过字符串类名和反射延迟加载，保证 1.12.2 Java 8 启动阶段不会解析 Java 17 class。
- Folia 判断必须用真实 Folia 与现代 Paper 对照验证，不能只凭某个 scheduler 方法存在。
- 每次改 universal 都必须用同一个 jar 跑 Legacy、Bukkit 1.13-1.15、现代 Paper、Folia 四端 smoke，并记录完整 console/latest 日志。

## 第一阶段落地顺序

1. 确认目标版本线和每条线必须支持/允许不支持的功能。
2. 建立多模块 Maven 项目骨架。
3. 先做 `core` 的纯清理策略和路由策略单元测试。
