### 首轮失败

首次启动暴露真实兼容错误：

```text
java.lang.NoSuchFieldError: Class org.bukkit.Material does not have member field 'org.bukkit.Material STAINED_GLASS_PANE'
```

修复：

- `GlobalTrashService` 不再直接引用 `Material.STAINED_GLASS_PANE`。
- 改为按字符串顺序解析 `BLACK_STAINED_GLASS_PANE`、`STAINED_GLASS_PANE`、`LEGACY_STAINED_GLASS_PANE`、`GRAY_STAINED_GLASS_PANE`、`GLASS_PANE`、`THIN_GLASS`。
- 所有候选都不可用时退回 `Material.STONE`。

## 2026-06-02 仙人掌和岩浆损坏回收补齐

用户继续要求补齐旧功能。本轮复盘旧插件 `Set.PersonalTrashCan.OriginalFeatureClearItemAddGlobalTrash` 后，确认新实现此前只做了 PDC owner 标记，没有承接旧配置里的 `UseModel` 和 `Delay`。

### 实现内容

- `TrashConfig.PersonalTrashConfig` 新增 `damageRecoveryMode` 和 `damageRecoveryDelaySeconds`。

## 2026-06-02 Folia region-safe 清理入口补齐

前面 Folia 首轮 smoke 已证明普通 Bukkit 风格的 `world.getEntities()` 不能放在 global scheduler 上。本轮继续收口旧功能时，先把 Folia 清理从“拒绝危险扫描”推进到“专用 region/entity scheduler 清理”，但不把整产物声明为 `FOLIA_REGION_SAFE`，因为共享实体数量限制还没有 Folia 专用实现。

### 实现

- 新增 `FoliaRegionCleanupFeature`：
  - global scheduler 只负责收集世界和已加载 chunk。
  - 每个 chunk 交给 `Bukkit.getRegionScheduler().run(...)` 读取 `chunk.getEntities()`。
  - 物品所在 region 只读取物品实体和快照。
  - 世界垃圾桶写入先取位置快照，再切到箱子所在 region 调 `routeWorldTrashAt(...)`。
  - 路由成功后通过 `item.getScheduler().execute(...)` 回到物品实体 region 删除掉落物。
  - 清理统计使用线程安全增量方法累计，完成后输出 `[FoliaCleanup]` 汇总日志。
- `BLWorldTrashCanFoliaPlugin` 不再注册共享 `CleanupFeature`，改注册 `FoliaRegionCleanupFeature`。
- Folia `/blwtc clear` 改为异步启动语义：命令只提示已启动，最终结果看后台 `[FoliaCleanup]` 或后续 `/blwtc stats`。
- `FoliaPlatform` 增加 `SCHEDULER_REGION` 能力，但仍不声明 `FOLIA_REGION_SAFE`。
- Folia 产物暂不注册共享 `EntityLimitFeature`，避免 `world.getEntities()` / `getNearbyEntities()` 在 Folia 上跨 region 访问。
- Folia 后台测试入口 `debugworldtrash`、`debugroute`、`debugdrop`、`debugdamage` 改为提交到玩家实体 scheduler 执行，减少测试命令自身造成的 Folia 线程噪声。

## 2026-06-02 Folia 专用实体限制补齐

上一轮 Folia 清理补齐后，旧功能矩阵里还剩实体数量限制在 Folia 产物中被安全禁用。本轮补 Folia 专用实现，避免共享 `EntityLimitFeature` 里的 `world.getEntities()` 和 `getNearbyEntities()` 跨 region 访问。

### 实现

- 新增 `FoliaEntityLimitFeature`。
- 通过 `EntityAddToWorldEvent` / `EntityRemoveFromWorldEvent` 维护 `world + entityType` 数量缓存。
- 启用实体限制时，使用 global scheduler 分派已加载 chunk，再用 `RegionScheduler` 在 chunk 所在 region 内读取 `chunk.getEntities()`，定期复算缓存。
- `CreatureSpawnEvent` 中按缓存判断单世界实体上限；放行时立即按实体 UUID 预占计数，避免同一 tick 连续生成绕过上限，后续 `EntityAddToWorldEvent` 用 UUID 去重，不会双计数；如果实体没有进入可调度状态或下一 tick 已无效，会释放预占计数。
- 密集实体限制不再调用 `getNearbyEntities()`，只扫描当前 chunk 内、半径范围内的同类型实体；这是为了保持 Folia region-safe，代价是跨 chunk 边界的密集实体不会在这一轮被同一次生成事件清理。
- `BLWorldTrashCanFoliaPlugin` 接回实体限制功能，但注册的是 Folia 专用 `FoliaEntityLimitFeature`。

## 2026-06-03 玩家掉落 owner 追踪补齐

### 背景

继续审计旧配置 `Set.PersonalTrashCan.NoWorldTrashCanEnterPersonalTrashCan` 时发现，新架构把它迁移到 `personal-trash.track-player-dropped-items`，但普通清理只读取 `ItemSnapshot.ownerUuid`。Paper/Folia 可以通过 PDC 读取 owner，Legacy 1.12 和 Bukkit 1.13-1.15 没有 PDC，因此玩家主动丢弃物在“没有可用世界垃圾桶”时会退到公共垃圾桶，不能按旧语义优先进入个人垃圾桶。

旧插件该功能本身要求高版本持久 PDC，低版本无法做到“重启后仍有效”。本轮补齐的是当前运行态内的短期 owner 追踪：玩家丢弃事件记录 `Item UUID -> Player UUID`，普通清理和损坏回收都可以读取；过期或路由完成后立即释放，避免长期占用内存。

### 修改

- 新增 `DropOwnerTracker`，保存短期掉落物归属和过期时间。
- `TrashFeature` 玩家主动丢弃时继续调用平台 PDC 标记，同时把掉落实体写入 `DropOwnerTracker`。
- 追踪时间至少 60 秒；如果自动清理间隔更长，则覆盖一轮清理间隔再多 5 秒。
- `CleanupFeature` 和 `FoliaRegionCleanupFeature` 生成 `ItemSnapshot` 后，如果 PDC owner 为空，则用短期 owner 记录补齐。
- 成功路由或删除后移除 owner 记录。
- 四个平台入口共享同一个 `DropOwnerTracker`。
- 四个平台 `debugdrop` 测试命令在生成掉落物后设置 `pickupDelay=200`，避免测试夹具把物品生成在玩家脚下后被立即捡回，导致清理扫描不到实体。

## 2026-06-03 Paper/Folia PDC 归属标记叠加修复

用户指出 PDC 可能导致物品无法正常叠加。复核当前实现后确认：此前 Paper/Folia 的 `markOwner` 把 `player_uuid` 写进 `ItemStack` 的 `ItemMeta` PDC，Bukkit 叠加判断会比较物品元数据，因此不同 owner 或带/不带 owner 的同类物品可能无法正常叠加，且被写入垃圾桶后仍可能带隐藏标记。

### 修复内容

```text
ItemSnapshotMapper 新增 toSnapshot(Item) 和 sanitizeForStorage(ItemStack) 默认方法。
PaperItemSnapshotMapper / FoliaItemSnapshotMapper:
  - markOwner 改为写入掉落实体 Item 的 PDC。
  - toSnapshot(Item) 优先读取掉落实体 PDC。
  - 兼容读取旧 ItemStack PDC，避免旧掉落物归属丢失。
  - sanitizeForStorage 会删除旧 ItemStack 上的 player_uuid PDC。
GlobalTrashService / PersonalTrashService / WorldTrashRouter:
  - 容量判断和入库写入前统一使用 sanitizeForStorage。
TrashFeature:
  - 真实玩家丢弃和 debugdrop owner 共用 trackDroppedItem，保证测试夹具也走平台 owner 标记。
```

这样 Paper/Folia 新生成的 owner 标记只存在于掉落实体，不污染物品本身；进入世界、公共、个人垃圾桶前会清理旧版本残留在物品元数据上的内部标记。

## 2026-06-03 reload 补齐缺失默认配置

用户反馈：删除多个 yml 配置文件后执行 `wtc reload`，插件不会把缺失的默认 yml 重新生成。这个行为会让服主误删配置后只能重启服务端才能恢复，属于 reload 自愈缺口。

### 根因

四个平台入口在 `onEnable()` 中会调用 `saveDefaultConfigs()`，但 `reloadPlugin()` 只执行 `reloadConfig()`、读取拆分配置和刷新功能模块。也就是说，默认资源释放只发生在启动阶段，运行中删除 `cleanup.yml`、`trash.yml`、`messages/*.yml` 等文件后，reload 直接读取缺失文件，自然不会补回。

### 修复内容

```text
BLWorldTrashCanLegacyPlugin.reloadPlugin()
BLWorldTrashCanBukkitPlugin.reloadPlugin()
BLWorldTrashCanPlugin.reloadPlugin()
BLWorldTrashCanFoliaPlugin.reloadPlugin()
```

四个平台 `reloadPlugin()` 开头统一先调用 `saveDefaultConfigs()`，再执行 `reloadConfig()`、`loadConfigBundle()`、`messageService.reload(...)` 和 `featureRegistry.reloadAll()`。

`saveDefaultConfigs()` 内部仍只调用 `saveDefaultConfig()` 和 `saveResourceIfMissing(...)`，因此只会补齐缺失文件，不会覆盖服主已有配置。

### 构建和静态检查

本机 `mvn` 仍不在 PATH，本轮只改四个平台入口类，使用当前已验收 staging 目录增量编译入口 class，并用 JDK 21 `jar.exe` 更新四个 dist jar。

## 2026-06-18 实体密度低占用扫描落地

用户确认清理插件最忌讳自身占用高，本轮把世界实体数量限制和密集实体限制从“事件里同步扫描附近实体/已加载实体”的思路，改为低占用分片扫描体系。

### 实现调整

- 新增 `LowOverheadEntityLimitEngine`，统一处理 dirty chunk、loaded chunk 分片、不可变实体快照、异步候选计算、TTL、去重、最大队列、重试上限和统计。
- 普通 Bukkit/Paper/Spigot 端的 `EntityLimitFeature` 改为主线程只按预算采集少量已加载 chunk 快照，异步 worker 只处理 UUID、世界、类型、chunk、坐标等轻字段，最终删除回到主线程并受 `max-removes-per-run` 限制。
- Folia 端的 `FoliaEntityLimitFeature` 改为 global region 只选择 chunk，快照采集和删除都派发到 chunk 所在 region，避免 global 线程直接访问实体。

## 2026-06-28 密集实体 remove-count 语义修复

用户指出旧项目虽然实现臃肿，但语义表达正常。本轮对照旧版 `org.worldlisttrashcan.system.limitentity.removeEntity` 和 `LimitMain` 后确认：旧配置 `GatherEntityLimitCount: 实体类型;数量;范围;清理数量` 的第四段表示“达到密集条件后本轮最多清理多少只”，不是“只清理超出上限的差值”。

重构版原问题：

- 候选创建时曾把清理数量截断为 `nearby.size() - max-count`，导致 `remove-count` 不能表达旧版语义。
- 删除阶段曾重新判断“是否仍超限”，前面的候选删除后可能导致同轮剩余候选被跳过。
- 单 chunk 内已做密集组去重，但跨 chunk 快照仍可能把同一半径内的密集群重复创建候选；Folia 真实客户端回归中暴露出 `remove-count: 5` 时单条正式提示“本次已清理 10 只”。

修复内容：

- `LowOverheadEntityLimitEngine` 按 `min(remove-count, nearby.size())` 创建候选。
- 删除阶段只校验候选仍存在、类型/世界/chunk/规则有效；密集规则关闭时旧候选会被消费，不再删除。
- 同一半径内如果已经有待删除候选，后续 chunk 快照跳过本组密集实体，避免跨 chunk 重复触发。
- 新增 `LowOverheadEntityLimitEngineSelfTest`，覆盖 `remove-count=5`、删除阶段不再因阈值变化跳过、关闭规则后不删除、跨 chunk 同组不重复创建候选。
- `tools/rgb-visual-matrix/run_entity_density_visual_matrix.py` 新增 `--remove-count` 参数，并校验正式提示中的“已清理”数值不超过本轮 `remove-count`。

## 2026-07-02 Vault 扣费 F-037 专项收敛

本轮继续收敛完整功能矩阵最后一个遗留项 `F-037`。该功能是玩家从个人垃圾桶取出物品时按 `trash.yml` 的 `personal-trash.take-cost` 调用 Vault Economy 扣费，必须用真实 Economy provider 和真实客户端 GUI 点击证明。

### 根因

首次 fake Vault/Economy 启动后，服务端已经加载插件名为 `Vault` 的临时夹具并注册 Economy，但 `BLWorldTrashCan` 输出：

```text
[BLWorldTrashCan] [Vault] Vault API 不可用，个人垃圾桶扣费自动关闭: net.milkbowl.vault.economy.Economy.withdrawPlayer(org.bukkit.entity.Player,double)
```

用 `javap` 确认 VaultAPI 1.7 的真实签名是 `withdrawPlayer(org.bukkit.OfflinePlayer,double)`，不是 `Player,double`。普通 `Player` 实现了 `OfflinePlayer`，但 Java 反射 `getMethod` 要求精确参数类型，因此 universal 总包此前会在真实 Vault 环境下关闭扣费。

同时检查个人垃圾桶取出流程发现一个真实业务风险：旧逻辑先扣费，再调用 `player.getInventory().addItem(...)`。如果玩家背包满或只能部分放入，会出现扣费成功但物品没有完整取出的情况。

### 修复

- `UniversalVaultPaymentService` 改为反射查找 `withdrawPlayer(OfflinePlayer,double)`。
- `PersonalTrashService.takeItem` 在扣费前调用 `InventorySlotUtil.hasStorageSpace(player.getInventory(), itemStack)`。
- `InventorySlotUtil` 新增 `hasStorageSpace`，只检查 Bukkit `Inventory#getStorageContents()`，避免把护甲槽、副手等非主背包槽误算成可存储空间。
- 四套平台默认语言文件都新增 `personal-trash.inventory-full` 和中文注释。
- 新增 `tools/rgb-visual-matrix/run_vault_payment_matrix.py`。脚本临时编译插件名为 `Vault` 的 fake Economy 夹具，打包完整 VaultAPI 类，备份/恢复测试服原有 `Vault*.jar`，并使用真实客户端点击个人垃圾桶 GUI。
