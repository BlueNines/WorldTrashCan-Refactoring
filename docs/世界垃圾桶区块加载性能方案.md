# 世界垃圾桶区块加载性能方案

## 问题

世界垃圾桶的位置保存在数据文件中。清理掉落物时，如果对一个未加载区块里的世界垃圾桶位置直接调用 `world.getBlockAt(x, y, z).getState()`，服务端可能会同步加载该区块。

这类同步区块加载发生在清理任务里时，会把一次后台清理变成磁盘区块读取，玩家多、垃圾桶多或区块很远时会明显卡顿。

## 原则

- 默认绝不为了写入世界垃圾桶而强制加载未加载区块。
- 世界垃圾桶只是优先回收目标，未加载时应跳过并降级到个人垃圾桶或公共垃圾桶。
- 只有服主明确配置允许时，才允许加载未加载区块，并且必须在配置注释和启动日志里提示风险。
- 统计和 debug 日志要能看出本轮跳过了多少个未加载区块位置。

## 推荐方案

### 方案 A：只写已加载区块

默认使用这个方案。

1. 读取世界垃圾桶位置前先计算区块坐标：
   - `chunkX = x >> 4`
   - `chunkZ = z >> 4`
2. 调用 `world.isChunkLoaded(chunkX, chunkZ)` 判断区块是否已经加载。
3. 如果未加载，跳过该位置，不调用 `getBlockAt`、`getState` 或任何可能触发区块加载的方法。
4. 如果所有世界垃圾桶位置都未加载，则视为世界垃圾桶当前不可用，清理路由继续尝试个人垃圾桶、公共垃圾桶，最后才删除。
5. debug 开启时输出：
   - 世界名
   - 垃圾桶位置
   - `skipped unloaded chunk`

优点：不改变玩家使用习惯，性能风险最低。

缺点：离线区块里的世界垃圾桶不会立刻接收清理物品。

### 方案 B：配置项允许强制加载

新增配置项：

```yaml
world-trash:
  # 是否允许世界垃圾桶写入未加载区块。
  # 默认 false。开启后清理任务可能同步加载区块，垃圾桶多或区块很远时会造成卡顿。
  allow-load-unloaded-chunks: false
```

只有该项为 `true` 时，才允许旧逻辑访问未加载区块。启动时如果检测到开启，应输出警告日志。

### 方案 C：长期虚拟世界垃圾桶

长期可以把世界垃圾桶改成“虚拟容器”：

1. 清理时只写插件自己的存储，不写真实箱子。
2. 玩家打开世界垃圾桶时，再把存储内容映射到 GUI。
3. 真实箱子只作为创建标记和入口，不再作为清理写入目标。

优点：完全避免区块加载和箱子容量读写问题。

缺点：行为会明显偏离旧插件，迁移成本高，应该作为后续版本单独设计。

## 验收标准

- 注册一个位于未加载区块的世界垃圾桶后执行清理，服务端不加载该区块。
- debug 日志能看到该位置被跳过，原因是 `skipped unloaded chunk`。
- 同世界已加载区块里的世界垃圾桶仍能正常接收物品。
- 所有世界垃圾桶都未加载时，物品会降级进入个人垃圾桶或公共垃圾桶。
- 未开启 `allow-load-unloaded-chunks` 时，代码中不得在未加载区块路径调用 `getBlockAt/getState`。

## 后续落地顺序

1. 在 `trash.yml` 增加 `world-trash.allow-load-unloaded-chunks`，默认 `false`。
2. 在 `TrashConfig.WorldTrashConfig` 中读取该配置。
3. 在世界垃圾桶路由写入、统计和 debug 摘要中统一使用已加载区块检查。
4. 增加后台测试命令，注册远处未加载区块位置并验证不会加载区块。
5. 编译、真实测试服 RCON 验证、保留完整日志后提交。

## 2026-06-02 落地记录

已落地方案 A 和方案 B：

- `trash.yml` 新增 `world-trash.allow-load-unloaded-chunks`，默认 `false`，四个平台默认配置均带中文注释。
- `TrashConfig.WorldTrashConfig` 已读取该配置。
- `WorldTrashRouter` 在访问世界垃圾桶容器前先检查 `world.isChunkLoaded(chunkX, chunkZ)`；默认未加载时直接跳过，不调用 `getBlockAt()` / `getState()`。
- `allow-load-unloaded-chunks: true` 时保留旧行为，并在加载世界垃圾桶数据时输出性能风险警告。
