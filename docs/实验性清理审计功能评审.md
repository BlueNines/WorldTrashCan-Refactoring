# WorldListTrashCan 实验性清理审计功能评审

## 文档状态

- 当前阶段：需求与架构评审。
- 当前结论：方案可实现，但尚未开始编码。
- 功能定位：实验性、非关键、可完全关闭，未来可能删除或转为稳定功能。
- 交付形式：直接包含在 WorldListTrashCan 的现有插件 Jar 中，不建立 expansions 扩展加载系统，也不拆成独立 Bukkit 插件。
- 本文中的“清理审计收口”是插件内部调用入口，不是 Bukkit `Listener`，也不监听服务器上所有实体移除事件。

## 一、需求目标

扫地完成后，插件可以保存本次清理的时间、触发方式和被清理物品的完整序列化信息。管理员可以通过只面向 OP 的“查水表”菜单查看近期清理批次，并异步加载某次清理中的物品详情。

该功能必须满足以下前提：

1. 审计功能不能决定物品是否被清理或进入垃圾桶。
2. 数据库失败、队列已满、序列化失败时，只允许丢弃审计数据，不能中断扫地。
3. 默认关闭，关闭后不得留下数据库连接、线程、任务、监听器、GUI 或物品序列化开销。
4. Spigot、Paper、Folia 和 universal 总包共用同一套审计业务，不复制实现。
5. SQLite 和 MySQL 只能选择一个，不能同时连接两个数据库。
6. 审计表必须与插件其他数据库表使用同一个已配置数据库，不能为了日志单独跨库连接。
7. 默认只保留最近 7 天，过期记录自动删除。

## 二、评审结论

### 2.1 采用统一收口，但不采用全局事件监听

用户提出的“Folia 和普通 Spigot 服务器共同使用一个监听器统一收口，关闭收口就关闭功能”方向是正确的。

实现时不建议注册一个监听所有实体删除行为的 Bukkit 事件监听器，原因如下：

- 无法准确区分 WorldListTrashCan 清理、原版死亡、其它插件删除和区块卸载。
- 可能重复记录或漏记。
- 高频实体事件会产生无意义调用，增加服务器负担。
- Folia 中实体可能分属不同区域线程，全局监听后再访问实体会增加线程风险。

最终采用插件内部的 `CleanupAuditRecorder` 收口。每轮清理先取得一个很轻的 `CleanupAuditSession`，只有 WorldListTrashCan 已经成功处理物品后，才把结果交给本轮会话：

```text
普通 Spigot/Paper 清理线程 ─┐
                           ├─> CleanupAuditSession ─> 有界队列 ─> 异步数据库写入
Folia 实体所属区域线程 ─────┘
```

这只是一个很小且有实际价值的边界，不继续增加事件总线、工厂、扩展 ClassLoader 或多套监听器。

### 2.2 关闭时使用空实现

清理主流程只持有一个 `CleanupAuditRecorder`。功能关闭或队列已满时，`beginRun` 返回立即结束的空会话，而不是在多个清理分支中反复判断配置：

```java
CleanupAuditSession session = auditRecorder.beginRun(cleanupContext);
session.recordItem(itemStack);
session.complete(partial);
```

`recordItem` 必须由物品当前所属的合法服务器线程调用。空会话会在读取、复制和序列化 `ItemStack` 前直接返回。

关闭状态的硬性标准：

- 审计物品复制次数为 0。
- Bukkit/YAML 序列化次数为 0。
- 数据库驱动初始化次数为 0。
- 数据库连接数为 0。
- 审计线程数为 0。
- 过期清理任务数为 0。
- 审计 GUI 监听器注册数为 0。
- 审计队列和批次缓存为空。

收口判断必须位于物品复制和序列化之前，否则“关闭功能”仍然会消耗 CPU 和内存。

### 2.3 一次扫地对应一个批次

一次定时扫地或一次 `/wtc clear` 对应一条清理批次记录。

普通 Spigot/Paper 可以在本轮扫描结束后直接提交完整批次。Folia 会在多个区域线程中产生批次片段，因此需要：

1. 清理开始时生成唯一的运行期批次 ID，并尝试为本批次预留一个有界队列名额。
2. 如果没有队列名额，立即返回空会话，本轮不执行任何审计序列化。
3. 各区域只提交同一批次 ID 下的不可变片段。
4. 全部区域完成、超时或取消时关闭批次。
5. 关闭后的批次才允许进入数据库写入队列。
6. 超时批次可以记录为 `partial: true`，但不能无限等待区域回调。

批次缓存必须有数量上限和超时时间。已关闭、已超时或插件停用的批次必须及时移除，避免内存泄漏。

## 三、线程边界

### 3.1 必须在服务器合法线程完成的工作

以下操作不能丢给普通异步线程：

- 读取和复制 `ItemStack`。
- 读取 `ItemMeta`。
- 调用 Bukkit 的物品序列化和反序列化方法。
- 创建或修改 Inventory。
- 打开、刷新和关闭玩家 GUI。

普通 Spigot/Paper 在主线程执行；Folia 在实体所属区域线程或玩家实体调度线程执行。

### 3.2 可以异步完成的工作

- 对已经生成的字符串或字节计算 SHA-256。
- GZIP 压缩和解压缩。
- SQLite/MySQL 事务和 JDBC batch。
- 查询清理批次和物品数据。
- 删除过期数据。
- 把查询结果整理为不含 Bukkit 对象的不可变 DTO。

异步阶段禁止长期持有 `Entity`、`World`、`Player`、`Inventory` 或 `ItemStack`。

## 四、物品序列化方案

### 4.1 数据来源

首版只记录“扫地流程中已经成功处理的物品实体”。不监听仙人掌、岩浆、虚空、玩家手动放入垃圾桶或其它插件删除物品的行为。

是否把普通生物、投射物和经验球数量写入批次统计可以后续增加，但它们没有 `ItemStack` 序列化数据，不能混入清理物品表。

### 4.2 序列化时机

序列化发生在物品仍处于合法服务器线程、并且清理主流程已经确认处理成功之后。推荐顺序：

```text
确认路由或删除成功
  -> 判断审计收口是否启用
  -> clone ItemStack
  -> Bukkit/YAML 完整序列化
  -> 生成不可变片段
  -> 投递有界队列
```

任何审计异常都必须在收口内部截断，不能反向抛给清理流程。

### 4.3 同类物品聚合建议

为了减少数据库体积，建议在同一清理批次内合并序列化内容完全相同的物品：

- 用数量为 1 的克隆物品生成标准化序列化内容。
- 用标准化内容的 SHA-256 作为快速分组依据。
- 同时保存实际物品总数和原始堆叠数量。
- 哈希相同时仍比较完整内容，不能只靠哈希判定相同。
- 不跨清理批次去重，避免过期删除时产生复杂引用关系。

这样可以完整保留材质、显示名、Lore、附魔、NBT/PDC 等 Bukkit 能够序列化的信息，又不会把 4096 个相同石头保存为几十条重复大文本。

不同版本无法识别的历史物品不能让整个菜单加载失败。反序列化失败时应显示一个“无法在当前版本还原”的替代物品，并在 Lore 中保留原材质名、服务端版本和错误摘要。

## 五、数据库设计

### 5.1 清理批次表

建议表名：`wtc_cleanup_run`

| 字段 | 含义 |
| --- | --- |
| `id` | 数据库自增主键 |
| `cleaned_at_ms` | 清理时间的 Unix 毫秒时间戳，用于排序和过期判断 |
| `cleaned_at_text` | `yyyy-MM-dd HH:mm:ss.SSS` 格式的可读时间 |
| `trigger_type` | `scheduled`、`manual` 等触发方式 |
| `total_item_amount` | 本次成功处理的物品实际总数 |
| `distinct_item_count` | 本次不同序列化物品数量 |
| `partial` | Folia 超时或部分回调失败时是否为不完整记录 |

### 5.2 清理物品表

建议表名：`wtc_cleanup_item`

| 字段 | 含义 |
| --- | --- |
| `id` | 数据库自增主键 |
| `cleanup_id` | 所属清理批次 ID |
| `item_order` | 同一批次中的稳定展示顺序 |
| `material` | 材质枚举名，便于后台快速查看 |
| `display_name` | 物品显示名，没有则保存空文本 |
| `total_amount` | 聚合后的实际物品总数 |
| `stack_count` | 聚合前的物品实体或堆叠数量 |
| `serialized_data` | 压缩后的完整标准化序列化数据 |
| `serialized_sha256` | 未压缩标准化内容的 SHA-256 |
| `server_version` | 生成该序列化数据时的服务端版本 |

父子关系使用外键：

```sql
FOREIGN KEY (cleanup_id)
REFERENCES wtc_cleanup_run(id)
ON DELETE CASCADE
```

不在父表中保存“物品 ID 字符串列表”。父子表已经能准确表达关系，字符串列表会造成双份状态、删除不一致和额外解析开销。

SQLite 每次建立连接后都必须执行：

```sql
PRAGMA foreign_keys = ON;
```

### 5.3 保留时间

- 默认保留 7 天。
- 过期判断只使用 `cleaned_at_ms`，不解析可读时间文本。
- 删除过期父记录时依靠 `ON DELETE CASCADE` 删除物品数据。
- 启动后延迟执行一次检查，之后低频定时检查，不在每次扫地后全表扫描。
- 清理使用索引和有限批次删除，避免一次事务删除大量历史数据造成长时间锁表。

### 5.4 SQLite、MySQL 和 Redis 结论

- 首版支持 SQLite 和 MySQL，配置只能二选一。
- SQLite 适合默认单服使用，文件建议放在 `plugins/WorldListTrashCan/data/cleanup-audit.db`。
- MySQL 使用插件当前配置的同一个业务数据库，审计表与其它业务表同库。
- 首版不做 Redis。Redis 的 Key TTL 不能自动清理 Sorted Set 等查询索引，完整物品序列化数据也会占用较多内存，最终仍需要额外索引维护逻辑。
- JDBC 驱动直接包含在现有插件 Jar 中；功能关闭时不得主动加载驱动。Jar 磁盘体积会增加，但关闭功能时不应增加运行线程和数据库内存占用。

## 六、性能和故障隔离

### 6.1 有界队列

数据库写入使用固定容量队列，禁止无限增长。建议初始限制：

```yaml
limits:
  # 等待异步写库的最大清理批次数；满后丢弃新的审计记录，不阻塞扫地。
  queue-capacity: 128
  # 单次清理最多保留多少种不同序列化物品。
  max-distinct-items: 256
  # 单个物品允许生成的最大未压缩字节数。
  max-bytes-per-item: 262144
  # 单次清理允许生成的最大未压缩字节数。
  max-bytes-per-cleanup: 4194304
```

清理开始时应先尝试预留队列容量。队列已经达到上限时，本轮直接取得空会话，避免先序列化大量物品再发现无法入队。

超过限制时：

- 正常扫地继续完成。
- 当前审计记录标记为 `partial` 或直接丢弃。
- 控制台使用限频警告，不能每个物品刷一条错误。
- 不无限重试，不把失败数据写入无限增长的内存补偿队列。

### 6.2 数据库线程

- 默认只使用一个审计写入线程，顺序处理清理批次。
- 一次清理批次使用一个事务和 JDBC batch 写入。
- 不为每个物品提交一次数据库任务。
- 查询任务与写入任务可以共用一个小型有界执行器，首版不引入连接池框架。
- MySQL 断线后允许下一次任务重新建连，但必须有限重试和限频日志。

### 6.3 插件关闭和 reload

关闭审计功能时按以下顺序处理：

1. 先把收口切换为空实现，阻止新数据进入。
2. 注销审计命令入口和 GUI 监听逻辑。
3. 取消过期清理任务。
4. 给正在写入的数据一个很短的有界结束时间。
5. 超时后丢弃剩余非关键审计数据。
6. 关闭连接、线程和队列引用。

不能为了保存审计数据让服务器关闭或 `/wtc reload` 长时间卡住。

## 七、配置文件草案

建议生成独立文件：`experimental/cleanup-audit.yml`

所有正式配置项落地时必须补充详细中文注释。以下只用于评审字段和默认值：

```yaml
# 实验性清理审计功能总开关。
# 关闭后不会序列化物品、创建数据库连接、启动线程或注册审计菜单。
enabled: false

# 数据保留天数；超过时间的清理批次和所属物品会自动删除。
retention-days: 7

storage:
  # 可选 sqlite 或 mysql，同一时间只能使用一种存储。
  type: sqlite

  sqlite:
    # 相对于 plugins/WorldListTrashCan 的数据库文件路径。
    file: data/cleanup-audit.db

  mysql:
    host: 127.0.0.1
    port: 3306
    database: test
    username: root
    password: change-me
    # 数据表名前缀，不能用于切换到另一个数据库。
    table-prefix: wtc_

limits:
  queue-capacity: 128
  max-distinct-items: 256
  max-bytes-per-item: 262144
  max-bytes-per-cleanup: 4194304

gui:
  # 查水表菜单每页显示的清理批次数量，最大不能占用底部导航行。
  runs-per-page: 45
  # 详情菜单每页显示的不同物品数量。
  items-per-page: 45
```

数据库密码不能输出到日志、状态命令或错误堆栈整理信息中。

## 八、查水表菜单

### 8.1 入口

- 建议命令：`/wtc audit`。
- 建议权限：`WorldListTrashCan.audit`，默认只授予 OP。
- 审计关闭或初始化失败时，命令只提示功能未启用，不创建数据库资源。

### 8.2 清理记录菜单

- 异步查询最近保留期内的清理批次。
- 回到玩家所属线程后创建 GUI。
- 每次清理使用一个泥土物品表示。
- 物品名称格式：`26年7月21日17时16分38秒`。
- 同一秒内存在多条记录时允许出现多个同名物品，按毫秒时间和自增 ID 保持稳定顺序。
- Lore 显示触发方式、实际物品总数、不同物品数、是否为不完整记录，以及“点击查看物品详情”。
- 底部提供上一页和下一页。

### 8.3 清理详情菜单

- 点击记录后先显示加载状态，不能在玩家线程执行数据库查询。
- 数据库按页查询当前最多 45 种物品，不能一次读取并反序列化整批全部物品。
- 当前页异步查询完成后，回到玩家所属线程执行本页反序列化并打开详情菜单。
- 标题格式：`26年7月21日17时16分38秒清理的物品列表`。
- 每种标准化序列化物品显示一个样品，Lore 追加实际总数和原始堆叠数。
- 最下面一行提供上一页、中间屏障返回清理记录菜单、下一页。
- 翻页时继续按页异步查询，只在玩家线程反序列化当前页最多 45 个样品。
- 数据库查询失败或玩家已经离线时直接结束，不持有玩家对象重试。

## 九、尚待用户确认的产品细节

以下内容尚未定案，实现前需要确认：

1. **详情 GUI 是否只读。** 强烈建议只读。如果允许拿取历史物品，会无限复制已经被清理的物品；如果允许放入，数据库内容不会同步，还可能在关闭菜单时造成玩家物品丢失。
2. **是否记录空清理。** 建议没有清理任何物品时不建立数据库记录，避免定时任务产生大量无意义行。
3. **详情展示方式。** 建议每种完整属性相同的物品显示一个样品，并在 Lore 显示总数量；不建议把 4096 个石头展开为 64 个槽位。
4. **记录范围。** 当前建议只记录定时扫地和 `/wtc clear` 中成功处理的物品实体，不记录玩家手动放入、仙人掌、岩浆、虚空和其它插件删除。
5. **批次统计范围。** 是否需要在清理批次表中额外保存生物、投射物、经验球等非物品实体的分类数量。
6. **超时批次。** 建议 Folia 某些区域超时后保存已完成部分并标记 `partial: true`，而不是完全丢弃。

## 十、实施顺序

1. 先把确认后的需求写入完整功能矩阵并分配新功能 ID。
2. 增加独立配置文件、类型化配置和配置解析测试。
3. 建立 `CleanupAuditRecorder` 空实现、启用实现和不可变批次 DTO。
4. 在普通清理与 Folia 区域清理的成功处理点接入统一收口。
5. 实现有界队列、SQLite/MySQL 表结构、事务批写和级联过期删除。
6. 实现 OP-only 清理记录菜单、异步查询、玩家线程回调、详情分页和返回。
7. 补充命令帮助、权限、多语言消息、README 和完整中文配置注释。
8. 完成后台自动化测试后，再进行真实服务端和真实客户端验收。

## 十一、最低验收标准

### 11.1 关闭状态

- Paper/Spigot 和 Folia 中均证明序列化次数、数据库线程数、连接数和队列长度为 0。
- 定时扫地、手动扫地、公共/个人/世界垃圾桶和实体限制功能结果与当前基线一致。
- 压力测试对比关闭审计前后，不能出现持续内存增长或额外数据库线程。

### 11.2 SQLite

- 正常写入清理批次和物品子表。
- 物品 NBT/PDC、显示名、Lore、附魔和新版本材质能够重新显示。
- 过期父记录删除后，子记录通过外键级联删除。
- 数据库文件锁定、损坏或不可写时，扫地主流程仍正常。

### 11.3 MySQL

- 只连接配置中的一个数据库。
- 审计表与其它插件业务表位于同一个数据库。
- 断线、密码错误、表创建失败和写入超时不能影响扫地。
- 批量写入使用事务和 JDBC batch，不逐物品提交。

### 11.4 队列与上限

- 队列满后只丢弃审计记录，扫地继续成功。
- 超大物品数据和单次大量不同物品受到字节数、种类数和队列容量限制。
- 警告日志限频，不能造成控制台刷屏。

### 11.5 真实客户端

至少使用当前 universal 整包在以下环境验收：

- Paper 1.12.2。
- 普通 Spigot 现代版本。
- Folia 1.21.8。

客户端截图必须覆盖：

- 清理记录菜单。
- 同一秒多条记录的稳定展示。
- 异步加载状态。
- 详情物品的名称、Lore、附魔或其它可见元数据。
- 上一页、下一页和返回按钮。
- 无权限玩家无法打开菜单。
- 审计关闭后的玩家提示。

服务端证据必须覆盖数据库表、写入记录、级联删除、断线容错、队列满和 reload 资源释放。截图完成后还要逐张重新读取，确认画面确实能够证明对应验收项，不能只以脚本退出码判定通过。

## 十二、明确禁止事项

- 禁止异步读取、复制、序列化或反序列化 Bukkit `ItemStack`。
- 禁止监听全服所有实体移除行为作为审计数据来源。
- 禁止数据库成功后才允许物品被清理。
- 禁止数据库异常传播到扫地主流程。
- 禁止无界队列、无界缓存和无限重试。
- 禁止为每个物品创建数据库任务或提交一次事务。
- 禁止 SQLite 与 MySQL 同时启用。
- 禁止审计日志连接到不同于插件业务配置的另一个数据库。
- 禁止关闭功能后仍然保留线程、连接、任务或序列化开销。
- 禁止为了这一项实验功能建立公开扩展生态、独立插件或复杂 ClassLoader 系统。
